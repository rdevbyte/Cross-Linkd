# Directory taxonomy

CrossLinkd's directory taxonomy is **Industry → Category → Profession → Services**. The canonical runtime source is `src/data/industries.ts`, which combines the preserved legacy catalog in `src/data/industries.base.ts` with `src/data/taxonomy-extension.ts`. Categories/professions keep stable slugs unless a historical duplicate or collision requires a canonical replacement. `validateTaxonomy()` checks hierarchy content and integrity; `scripts/taxonomy.test.mjs` protects required coverage, fallbacks, aliases, selection hierarchy, and search compatibility.

## Compatibility rules

- Category slugs are globally unique and remain unchanged when a category is moved to a better industry parent. `LEGACY_CATEGORY_PARENTS` accepts the prior Industry → Category pairs for existing clients and saved forms.
- Existing top-level and profession slugs that were not canonical are resolved by `LEGACY_INDUSTRY_SLUG_ALIASES` and `LEGACY_PROFESSION_SLUG_ALIASES`. Listing reads, search filters, profile routes, and writes normalize these identifiers; migration `0006_taxonomy.sql` renames the profession rows that were canonically renamed while their listing foreign keys remain attached to those rows.
- `legal-service-industry` is the top-level legal slug because `legal-services` is a longstanding category slug. The old industry interpretation of `legal-services` remains resolvable in industry context; the category slug remains intact in category context.
- “Other Industry,” “Other Category,” and “Other Professional or Service Provider” are universal fallbacks. A free-text category is still stored in `custom_category`; custom professions are stored in `listings.custom_professions`; selected and custom service labels are stored in `listing_services`. Taxonomy example services link to their profession through the optional `listing_services.profession_id`; genuinely custom services can leave that foreign key empty.

## Persistence and rollout

The Drizzle schema and migration `0006_taxonomy.sql` add aliases, keywords, service examples, and custom-profession storage. The seed script upserts the complete hierarchy and updates moved categories to their canonical parent; it is safe to rerun. For an existing database, back it up, apply migrations with `npm run db:migrate`, then synchronize the catalog with `npm run db:seed -- --taxonomy` (or `npm run db:seed` if you also want the other seed data) before deploying code that expects the new columns. Use the same production database for both commands: `db:migrate` uses `DIRECT_URL` (falling back to `DATABASE_URL`), while `db:seed` uses `DATABASE_URL`. The migrations are recorded and run once; the seed upserts taxonomy rows and is safe to rerun. Do not delete existing `listing_professions` join rows when a profession slug is renamed: the migration updates the referenced profession record in place when possible, and alias normalization remains available for compatibility.

Create/edit forms, dashboard editing, taxonomy-aware search, public profession routes, DB joins, and CSV/API form parsing use the normalized profession and service values. Custom profession/service text is intentionally accepted as user-entered directory metadata; this does not create any recommendation, licensing verification, or moderation functionality.

Listing writes validate every supplied industry, category, and profession before changing relation rows. Missing seeded taxonomy rows return a retryable service error; invalid values return a client error, and the transaction protects existing links from partial replacement. Owner PATCH merges omitted fields with stored values, including secondary industry links, professions, custom professions, and services. Public listing hydration includes those relations and does not truncate the published catalog at an arbitrary 500-row ceiling. Old primary slugs remain readable and searchable; a subsequent owner save writes canonical slugs. No listing data is deleted as part of compatibility handling.

Status policy is intentional: newly published submissions are public immediately; submit/resubmit on non-published listings enters `pending_review`; explicit draft saves stay private; ordinary saves of an already-published listing preserve `published` and its original publication timestamp. A published listing is hidden only when explicitly saved as a draft, archived, deleted, or otherwise changed by the authorized workflow. Search APIs use `Cache-Control: no-store` so a successful edit or status change is not masked by a stale response. Optional local taxonomy suggestions never participate in schema validation or persistence; manual selections remain authoritative.
